# Documents and Local AI

## Purpose

Tallystead stores receipts, invoices, statements, and general financial documents as household evidence. A document may be linked to a ledger transaction, but it is never itself a transaction and may remain unlinked indefinitely. Manual upload, review, matching, and metadata correction work without AI.

## Storage and access boundary

- PostgreSQL stores household-scoped metadata, checksums, match decisions, extraction results, and review disposition.
- MinIO stores original files and generated image thumbnails in the existing protected object-store volume.
- Originals and thumbnails are returned only through authenticated API routes with private, no-store cache headers. MinIO is not exposed to browsers.
- Supported uploads are PDF, JPEG, PNG, WebP, and plain text, up to 15 MiB per document. The server verifies the declared content type and records a SHA-256 checksum.
- Object keys are generated by the server and namespaced by household. User filenames are retained as display metadata, not used as object paths.
- Owner and Manager may upload, edit, match, extract, and delete. Contributor and Viewer may read shared household documents. Private per-member document scopes are a later explicit RBAC decision.
- Deleting a document removes its match/extraction records and its MinIO original and thumbnail. It never deletes or changes a ledger transaction.

PostgreSQL and MinIO are both included in the supported backup. A database-only restore is incomplete because document metadata would no longer have its corresponding objects.

## Document lifecycle

1. The client uploads base64 content and descriptive metadata through the authenticated API.
2. The API validates size and type, calculates the checksum, stores the original, generates a protected thumbnail for supported images, and commits metadata.
3. Tallystead calculates deterministic transaction candidates. The document remains unlinked until an Owner or Manager confirms a candidate or chooses a transaction manually.
4. If local AI extraction is enabled and configured, receipt and invoice uploads automatically queue an extraction. An Owner or Manager can also request extraction or retry from the document review. The worker records the provider, model, proposed fields, confidence, failure detail, and user disposition.
5. Accepting an extraction copies only selected descriptive fields to the document. It never changes a transaction, balance, split, reserve, bill, or reconciliation state.
6. A confirmed match may be removed later without altering either the document or transaction.

## Deterministic matching

Candidate matching is independent of AI and uses household ledger facts:

- exact absolute amount;
- document date within five days of the transaction date;
- the same account when the document specifies an account; and
- exact normalized payee agreement as additional evidence.

Candidates expose their evidence and confidence. Confirmation, rejection, and deferral are explicit review actions. A user may also select any eligible household transaction manually. Voided transactions cannot be matched. Match and unmatch actions are reversible and audited; the ledger record is not mutated.

## Local AI boundary

Local AI is optional and disabled until an Owner configures and enables it. The initial adapter supports Ollama and LM Studio-compatible local endpoints.

- Only loopback, Docker-service, `.local`, `.home.arpa`, or private-network runtime addresses are accepted. Public runtime URLs are rejected.
- Requests do not follow HTTP redirects, preventing a local endpoint from forwarding document content to a different destination.
- Image documents are submitted to a configured vision-capable model using the versioned `receipt-extraction-v1` contract. The model is asked to transcribe merchant/contact details, date/time, receipt number, subtotal, discounts, tax, tip, total, currency, payment method/card suffix, category hints, and individual line items with quantities, unit prices, totals, SKUs, and field confidence. Plain-text documents are submitted as text. PDFs use embedded text when present; scanned PDFs without embedded text fail safely and remain fully usable through the manual path.
- Tallystead normalizes the model response, rejects unsupported value shapes, and independently checks whether line items add to the subtotal and whether subtotal minus discounts plus tax and tip equals the total. Missing inputs or inconsistencies produce visible review warnings; they are never silently corrected.
- Every result is a suggestion with provider, model, confidence, raw structured output, status, and user disposition.
- Failed jobs retain a safe error and may be queued again. Worker interruption does not grant the output authority or modify financial records.
- Disabling AI stops new extraction processing and leaves documents, matching, imports, and ledger operations available.
- Owners can run a non-persistent vision test. Tallystead generates a synthetic receipt, confirms the configured model is advertised by the runtime, sends the image through the real extraction path, and reports model availability, response structure, merchant/date/amount/line-item accuracy, arithmetic consistency, and elapsed time. The synthetic image and result are not stored as household documents.

The application does not configure or call a cloud-AI provider. Operators are responsible for keeping the configured Ollama or LM Studio runtime inside their trusted household network and for choosing a model that supports the submitted content type.

## Review and recovery

- Users can inspect the protected original alongside a structured receipt review showing merchant, date/time, payment information, line items, totals, confidence, and arithmetic warnings before accepting metadata.
- AI-proposed payee, document date, total, currency, category hints, payment data, and line items are visibly separated from accepted document metadata. Accepting currently copies only merchant, date, total, and currency to reviewed document metadata; detailed receipt evidence remains attached to the extraction record.
- Rejecting an extraction preserves the result and records the decision; it does not erase evidence.
- An unlinked document is a valid state, not an exception.
- If object storage is temporarily unavailable, metadata remains intact and the object operation fails without writing partial ledger state. Restore both PostgreSQL and MinIO from the same backup set.

## Current limitations and extension points

- Phase 5 does not perform full OCR for image-only PDFs. A future local OCR adapter can produce text before the same extraction contract without changing document or ledger authority.
- One confirmed transaction match is supported per document. Multi-document-to-one-transaction is supported because each document owns its own match.
- Category hints are retained as suggestions and are not automatically resolved to or applied as category records.
- Phase 5B will extend category hints into a dedicated transaction-categorization review queue. Deterministic merchant rules and accepted household history take precedence; local AI may propose a category or splits with confidence and evidence, but an authorized user must accept or edit the proposal before the ledger changes.
- Email/IMAP document ingestion will use this same storage, provenance, extraction, and review pipeline when implemented; email credentials and messages remain separate integration records.
